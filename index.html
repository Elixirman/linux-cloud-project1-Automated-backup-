Simple Linux Projects for Cloud Engineers — Project 1

The Automated Backup Script

An examination of directory compression, timestamping, and failure-aware scripting, built around the permission model that governs real production systems.

Bash Scripting File Permissions Error Handling Automation

1. Overview

Cloud infrastructure accumulates data that cannot be easily reconstructed: application code, configuration files, database dumps, SSL certificates. The loss of any of these, without a copy stored elsewhere, constitutes an operational failure. The discipline that prevents this failure is backup automation — a script, run on a schedule, that performs the same protective action reliably and without a human deciding, each night, whether to remember to do it.

This project constructs that script. The exercise is not primarily about the tar command; tar is learned in an afternoon. The exercise is about a habit of mind common to cloud engineers: a repeatable manual task is encoded into a script, the script is made to fail loudly rather than silently, and its output is made predictable enough that another system — cron, a monitor, an on-call engineer — can trust it without reading the source.

What the finished script does

Core behavior

  • Accepts a source directory, such as /var/www/html
  • Produces a compressed .tar.gz archive
  • Names the archive with a timestamp
  • Writes the archive to a backup directory

Production requirements

  • Reports success or failure in plain language
  • Exits with a meaningful exit code
  • Validates that source and destination exist before acting
  • Operates correctly under a non-root user with read-only access to the source

2. The Production Model

Tutorials that back up a user's own home directory teach the mechanics of tar but skip the constraint that actually defines production work: the process performing the backup rarely owns the files it is backing up. A web application's files are typically owned by root or by a dedicated service account, while the engineer's own account — the one that will eventually run this script from cron — holds only enough privilege to read them.

This project is built under that constraint from the outset. A dedicated Linux user, referred to here as linux-guy, performs all of the work in this chapter. Directory creation and file ownership under /var/www/html require elevated privilege and are performed with sudo; everything downstream — reading the files, compressing them, writing the archive — is performed as an ordinary, unprivileged user. This separation is not an incidental detail. It is the reason the script must validate its inputs rather than assume they exist, and it is the reason file permissions, not merely file paths, become part of the design.

3. Provisioning the Production Source Directory

Requires sudo

The standard location for web content on a Linux server is /var/www/html. Because this path sits outside the home directory, its creation requires elevated privilege. The commands below create the directory, populate it with two representative files, and then adjust permissions so that an unprivileged user can read — but not modify — the contents.

# 1. Create the standard web directory sudo mkdir -p /var/www/html # 2. Create a dummy production file sudo sh -c 'echo "<h1>Production Website</h1>" > /var/www/html/index.html' sudo sh -c 'echo "db_password=supersecret" > /var/www/html/config.txt' # 3. Ensure your user can READ the files (but not modify them) sudo chmod -R 755 /var/www/html

Two details are worth pausing on. First, sudo sh -c '...' is required rather than sudo echo "..." > /var/www/html/index.html, because shell redirection (>) is interpreted by the current shell, which is not running as root — only the echo would run with elevated privilege, and the redirection itself would still fail with "Permission denied." Wrapping the entire command in sh -c and elevating that gives root the redirection as well.

Second, config.txt contains a plaintext credential. This is intentional: a realistic source directory sometimes contains files that should not exist in this form, and the security discussion in Section 9 returns to exactly this file.

After these commands, the directory is owned by root, and chmod -R 755 grants read and execute permission to all users — owner, group, and others — while restricting write access to the owner. This is the permission model a backup script will actually encounter: it can read everything under /var/www/html, but it did not create any of it and cannot change it.

4. The Backup Destination

Runs as linux-guy, no sudo required

Unlike the source directory, the backup destination is owned by the account that will run the script, since that account must be able to write new archives into it on every run.

mkdir -p ~/backups

No elevation is required here, and none should be. A script that needs sudo to write its own backups is a script whose blast radius, in the event of a bug, is far larger than it needs to be.

5. The Script

The script below is written for the production directory established in Section 3. It is created with nano, though any editor produces the same file:

nano ~/backup.sh
#!/bin/bash # ============================================ # Automated Backup Script # Compresses a target directory with a timestamp # ============================================ # --- Configuration (Variables) --- SOURCE_DIR="/var/www/html" BACKUP_DIR="$HOME/backups" TIMESTAMP=$(date +"%Y-%m-%d_%H-%M-%S") BACKUP_FILE="${BACKUP_DIR}/backup_${TIMESTAMP}.tar.gz" # --- Error Handling: Does the source exist? --- if [ ! -d "$SOURCE_DIR" ]; then echo "ERROR: Source directory '$SOURCE_DIR' does not exist." exit 1 fi # --- Error Handling: Does the destination exist? --- if [ ! -d "$BACKUP_DIR" ]; then echo "Backup directory not found. Creating '$BACKUP_DIR'..." mkdir -p "$BACKUP_DIR" if [ $? -ne 0 ]; then echo "ERROR: Failed to create backup directory." exit 1 fi fi # --- Perform the Backup --- echo "Starting backup of '$SOURCE_DIR'..." tar -czf "$BACKUP_FILE" -C "$(dirname "$SOURCE_DIR")" "$(basename "$SOURCE_DIR")" # --- Check if tar succeeded --- if [ $? -eq 0 ]; then echo "SUCCESS: Backup created at '$BACKUP_FILE'" ls -lh "$BACKUP_FILE" exit 0 else echo "ERROR: Backup failed." exit 1 fi

The file is saved (Ctrl+O, Enter, Ctrl+X in nano) and marked executable:

chmod +x ~/backup.sh

Note what did not change from a naive version of this script: no sudo appears anywhere in it. The 755 permissions set in Section 3 are sufficient for an unprivileged process to read and archive every file under /var/www/html. A backup script that requires root to run is a design flaw, not a convenience.

6. Execution and Verification

The script is run directly, as linux-guy, with no elevated privilege:

~/backup.sh

Its expected output:

Starting backup of '/var/www/html'... SUCCESS: Backup created at '/home/linux-guy/backups/backup_2026-09-14_20-35-12.tar.gz' -rw-r--r-- 1 linux-guy linux-guy 245 Sep 14 20:35 /home/linux-guy/backups/backup_2026-09-14_20-35-12.tar.gz

The archive's ownership is worth noting: even though the source files under /var/www/html are owned by root, the resulting .tar.gz is owned by the account that ran tar — linux-guy. Compression does not preserve the privilege boundary of the source; it produces a new, independent artifact owned by whoever created it.

The archive's integrity is confirmed by listing its contents without extracting them:

tar -tzf ~/backups/backup_*.tar.gz

A correct run lists html/index.html and html/config.txt, confirming that both files were captured.

7. Analysis of the Script

The interpreter directive

The first line, #!/bin/bash, is not a comment despite its appearance; it is a directive to the kernel specifying which interpreter should execute the file. In its absence, the system may fall back to sh, a more limited shell under which some Bash-specific syntax fails. Its inclusion is not optional in any script intended for reuse.

Variables and configurability

SOURCE_DIR="/var/www/html" BACKUP_DIR="$HOME/backups"

Paths are declared once, at the top of the file, rather than repeated inline throughout the script. This is not stylistic preference. When a backup destination changes — as it eventually will, often to an S3 bucket — a single line is edited instead of every occurrence of a hardcoded path. Configurability at the top of a script is one of the load-bearing habits of automation work.

On quoting: every variable expansion in this script is wrapped in double quotes. If a path ever contained a space — /home/john doe/backups, for instance — an unquoted expansion would split into two separate arguments and the command would fail in a way that is difficult to diagnose. Quoting is defensive, not decorative.

The timestamp

TIMESTAMP=$(date +"%Y-%m-%d_%H-%M-%S")

The $() construct is command substitution: the output of date, formatted according to the given string, is captured into a variable. Its purpose is uniqueness — without a timestamp, each run of the script would silently overwrite the previous backup, and the ability to restore to a specific point in time would be lost entirely. In a production incident, the question is rarely "do we have a backup?" but "do we have Tuesday's backup?" A timestamp is what makes that question answerable.

Hyphens and underscores are used deliberately in place of colons or slashes. Colons cause problems on some filesystems and in some tools; slashes would be parsed as directory separators. A naming convention is part of a script's interface, not an afterthought.

Constructing the output path

BACKUP_FILE="${BACKUP_DIR}/backup_${TIMESTAMP}.tar.gz"

The braces around each variable name disambiguate where the name ends and literal text begins. Without them, $BACKUP_DIR_file would be parsed as a reference to a variable literally named BACKUP_DIR_file, which does not exist. ${BACKUP_DIR} removes the ambiguity and is the convention used throughout production scripts.

Validating the source

if [ ! -d "$SOURCE_DIR" ]; then echo "ERROR: Source directory '$SOURCE_DIR' does not exist." exit 1 fi

The -d test evaluates whether the given path is a directory; the leading ! negates it. The condition reads, in full: if this path is not a directory, report the failure and stop. The exit 1 is the operative part. Every process on Linux returns a numeric exit status on completion — 0 for success, any nonzero value for failure. Once this script is invoked by cron (Project 2) or a monitoring system, that exit status is the only signal those systems have. A script that always exits 0, even after failing internally, converts every future failure into a silent one.

The compression command

tar -czf "$BACKUP_FILE" -C "$(dirname "$SOURCE_DIR")" "$(basename "$SOURCE_DIR")"
ElementFunction
tarTape archive — bundles multiple files into one
-cCreate a new archive
-zCompress the archive with gzip
-fSpecify the archive's filename (must be the final flag)
"$BACKUP_FILE"The output path
-C "$(dirname "$SOURCE_DIR")"Change into the parent directory before archiving
"$(basename "$SOURCE_DIR")"Archive only this folder, relative to that parent
Without the -C/dirname/basename combination, tar would store each file's full absolute path inside the archive — var/www/html/index.html rather than html/index.html. Extracting such an archive attempts to recreate that entire path structure from the filesystem root, which is rarely what is wanted and occasionally dangerous. Archiving relative to the parent directory produces a portable artifact that can be extracted anywhere.

Reporting the result

if [ $? -eq 0 ]; then echo "SUCCESS: ..." exit 0 else echo "ERROR: ..." exit 1 fi

The special variable $? holds the exit status of the immediately preceding command — here, tar. On success, the file size is printed via ls -lh as immediate visual confirmation; on failure, the script exits nonzero, and the calling context — a terminal, a cron job, a monitoring agent — is responsible for acting on that.

8. Architecture

Figure 1. Data flow from the privileged source directory through the unprivileged backup process to the resulting archive, with the two terminal exit states shown below.

Reading the diagram

The diagram traces two properties simultaneously: the flow of data, left to right, and the change of ownership at each stage. /var/www/html is owned by root; the script that reads it runs as an unprivileged user; the archive it produces is owned by that same unprivileged user. No stage in this flow requires the backup process to hold more privilege than it needs — the definition of least-privilege design.

The two branches at the bottom are not decorative. The red path — a failed validation or a failed tar invocation — terminates in exit 1. The green path terminates in exit 0. This is the entire interface a monitoring system needs: it does not read the script's logic, only its exit code.

Why this generalizes

At scale, this exact shape reappears with different names. The source directory becomes an EBS volume or an RDS snapshot. The script becomes a Lambda function or an SSM Run Command document. The backup destination becomes an S3 bucket governed by a lifecycle policy. The printed output becomes a CloudWatch log stream, and the exit code becomes the trigger for an SNS notification or a PagerDuty alert. The mechanics change; the shape — validate, act, report a status a machine can act on — does not.

9. Security Considerations

The provisioning step in Section 3 created config.txt containing db_password=supersecret in plaintext, then made it world-readable with chmod -R 755. This was done deliberately, to surface a problem that recurs constantly in real backup systems: a backup script that faithfully archives everything in its source directory will faithfully archive secrets that should never have been stored there in the first place.

The lesson, not just the fix: 755 permissions on a directory containing credentials mean that any local user on the system can read that password — not only the account performing backups. A production system would instead restrict such a file with something like chmod 640 and group ownership limited to the application's service account, or — preferably — remove the credential from the filesystem entirely in favor of a secrets manager (AWS Secrets Manager, SSM Parameter Store, Vault). The backup script did nothing wrong here; the exposure was already present in the source directory. A backup script is not a security boundary, and it should never be trusted to become one.

This distinction — between what the script is responsible for (reliable, verifiable archiving) and what it is not responsible for (deciding what belongs in the source directory) — is itself a production habit worth internalizing early.

11. Failure Modes

Missing execute permission

Running ~/backup.sh without a preceding chmod +x produces "Permission denied."

Unquoted paths containing spaces

tar -czf $BACKUP_FILE, without quotes, splits on any embedded space and fails unpredictably.

Whitespace around assignment

SOURCE_DIR = "/path" is invalid Bash; assignment permits no space on either side of =.

Checking $? after the wrong command

$? always reflects the immediately preceding command. An echo inserted between tar and the subsequent if [ $? ... ] check causes the script to evaluate echo's exit status — always 0 — rather than tar's.

12. Extension Exercises

Each exercise below is intended to be attempted individually, after the base script is verified to work.

1. Accept a command-line argument

Replace the hardcoded SOURCE_DIR with $1, allowing ./backup.sh /var/www/html to target any directory the invoking user can read.

2. Prune backups older than seven days

Append find "$BACKUP_DIR" -name "backup_*.tar.gz" -mtime +7 -delete. Unbounded retention is a real and common cause of disks filling silently in production.

3. Persist a log file

Redirect the script's output with >> /var/log/backup.log so that a history of runs survives beyond the terminal session that produced them.

4. Verify archive integrity

Run tar -tzf "$BACKUP_FILE" > /dev/null immediately after creation and check its exit status, confirming the archive is not corrupted before reporting success.

5. Address the credential in config.txt

Before adding cloud storage, resolve the issue raised in Section 9: either restrict config.txt to 640 with appropriate group ownership, or remove the secret from the filesystem in favor of a secrets manager.

6. Transmit to cloud storage

Copy the completed archive off-host with aws s3 cp "$BACKUP_FILE" s3://my-backup-bucket/, the point at which this exercise becomes indistinguishable from a real production backup pipeline.

13. Continuity to Project 2

Cron Job Automation

Once the script runs correctly by hand, Project 2 removes the human from the loop entirely: the script is scheduled to run every night at a fixed hour, unattended. Everything constructed here — the validated inputs, the meaningful exit codes, the timestamped and permission-aware output — is what makes an unattended nightly run trustworthy rather than a liability.
